# Glacial data privacy and disclosure boundary

Status: canonical technical privacy boundary for Glacial 0.9.7. This document describes current source behavior and focused G048/G049 evidence. It is not a public privacy notice, legal review, release-candidate acceptance, or claim of absolute security.

## Governing rule

Glacial may inspect untrusted project data locally, but it must not unnecessarily persist, disclose, export, log, transmit, or reproduce sensitive project content, credentials, secrets, tokens, or private host details. A local sink is not implicitly safe.

Operational absolute workspace and project-registration paths are the narrow exception: they remain in application-owned local state and local operational API/UI flows because Glacial must reopen, validate, scan, unregister, and write the selected project. They are prohibited from reports, Agent Remediation outputs, generated instructions, diagnostics, build/release records, and user exports.

`backend/app/privacy.py` is the Python enforcement source for secret redaction, control normalization, absolute-path replacement, safe project-relative paths, bounded excerpts, safe exception text, and recursive scan-value sanitization. `frontend/src/privacy.js` re-enforces the disclosure boundary for legacy API data, reports, and errors. ### G049 hexadecimal correction

G048 established the cross-surface privacy architecture, but its generic Python and frontend token logic incorrectly treated digest-shaped hexadecimal text and `sha*`/`cf*` prefixes as inherently safe. G049 corrects that boundary:

- Generic or untrusted text redacts bounded standalone 40–128 character hexadecimal runs by default, including runs in prose, evidence, errors, notes, descriptions, filenames, path segments, dependency metadata, child output, and frontend API errors.
- A `sha256:`, `sha384:`, `sha512:`, `cf..._`, or similar prefix is not a generic trust signal.
- Exact commits, SHA-256 checksums, snapshot digests, evidence/dependency/checkpoint fingerprints, signing pre/post hashes, certificate thumbprints, release-manifest hashes, and readiness commit references remain visible only through named field contracts with exact format validation.
- Malformed values in those structured fields are rejected or returned through ordinary sanitization rather than being trusted because they look digest-like.

## Network and external-process boundary

Production first-party runtime source opens only an owned loopback boundary:

- Rust binds no public listener. It starts the owned backend, generates a fresh 256-bit token, and sends only the token and application data directory to that child.
- Python binds an ephemeral listener to `127.0.0.1`; Uvicorn access logging, proxy headers, and server header are disabled.
- The Rust API bridge accepts only bounded `/api/...` paths and five methods, connects only to the supervisor-owned loopback endpoint, and attaches the token in memory.
- The frontend production CSP permits only Tauri IPC. Development CSP additionally permits the local Vite origin/WebSocket.
- No first-party updater, telemetry, analytics, crash reporter, cloud synchronization, remote resource loader, browser launcher, or general outbound HTTP client is present.
- The Tauri shell plugin has no frontend capability and is used by Rust only to start the packaged owned sidecar. Generated remediation instructions, finding commands, project scripts, and package installers are never executed.

Explicit build/release tools launch reviewed absolute executables without a shell. A configured signer and timestamp service may create an external network connection during a separately authorized signed build. The timestamp URL cannot contain credentials/query/fragment, provider environment values are explicitly allowlisted, and project-derived operational data is not an input to those tools. Package-manager network activity can occur only when a developer separately invokes install/build tooling; Glacial scanning and production runtime do not execute package installation.

Current source and targeted runtime evidence therefore support: **production project data does not leave the local machine; application traffic is authenticated loopback only.** This is not the broader claim “no network activity”: explicit dependency acquisition, signing, and timestamping tools can use external networks when separately invoked.

## Hostile fixtures and verification contract

G048 fixtures use deliberately fake canaries for Windows drive, UNC, user-profile, temporary and mixed-separator paths; Unicode path/name values; path-like notes/descriptions/exceptions; AWS/GitHub/bearer/password/private-key/`.env`/credential-URL/connection-string forms; secrets in source, filenames, dependency metadata, project descriptions, profile/review notes; and terminal controls/multiline values. G049 adds deterministic mixed-case 40-, 64-, 96-, and 128-character hexadecimal canaries across ordinary strings, evidence, errors, notes/descriptions, filenames/path segments, dependency metadata, child output, frontend errors, persistence, reports, remediation outputs, generated files, startup diagnostics, signing audits, and release manifests.

Tests require forbidden canaries and host fragments to be absent while retaining safe relative paths, rule IDs/versions, line numbers, dependency names/versions, counts, fingerprints, checksums, provenance, stable ordering, deterministic archives, and immutable scan rows. Operational root/registration paths are explicitly required to remain in their allowlisted database fields.

No real credential was used or reproduced in G048 or G049 fixtures, tests, documentation, logs, screenshots, handoffs, or artifacts.

## Installed G048 inspection
