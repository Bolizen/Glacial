# Glacial v1.0 remediation sequence

This sequence converts the P1 blockers and explicit P2 owner decisions in the 2026-07-27 audit into bounded future handoffs. It does not authorize v1.0.0, reserve work for P3 polish, or permit a handoff to weaken an existing safety or release gate.

## G045 — Versioned state lifecycle and recovery

- **Contract IDs:** `V1-SCAN-006`, `V1-DATA-001`, `V1-DATA-002`, `V1-DATA-004`, `V1-DATA-005`
- **Exact outcome:** inventory every persistent mutation; introduce an explicit database schema/migration and compatibility policy; add supported-predecessor fixtures, rollback/fault tests, backup/recovery guidance, and exact retention/reset behavior.
- **Why together:** these gaps share the SQLite/application-state trust boundary and must agree before desktop upgrade or uninstall behavior can be accepted.
- **Expected evidence:** schema/version documentation, migration fixtures, fault-injection results, SQLite integrity/readback, and a state-retention matrix.
- **Dependencies:** none.
- **Desktop computer-use acceptance:** limited interruption/recovery observation is required; full installer/portable acceptance waits for G052.
- **Release packaging/signing:** not required.
- **Validation scope:** targeted database, project lifecycle, scan persistence, baseline/profile, and interruption tests only.

## G046 — Persisted and exported data privacy boundary

- **Contract IDs:** `V1-FS-006`
- **Exact outcome:** enumerate every database, log, diagnostic, report, brief, package, release-log, and export field; document data classes and add focused tests preventing secrets, unnecessary project content, and absolute host-path disclosure.
- **Why together:** this is one cross-surface disclosure audit and should not be mixed with UI redesign or dependency work.
- **Expected evidence:** reviewed inventory, hostile fixture outputs, redaction/path tests, and explicit accepted fields for each surface.
- **Dependencies:** G045 state inventory.
- **Desktop computer-use acceptance:** focused log/report/export inspection required.
- **Release packaging/signing:** not required.
- **Validation scope:** targeted evidence, report, remediation, diagnostic, and persistence tests.

## G047 — Installed and portable desktop lifecycle

- **Contract IDs:** `V1-DESKTOP-002`, `V1-DESKTOP-003`, `V1-DESKTOP-004`, `V1-DESKTOP-005`
- **Exact outcome:** close confirmed lifecycle defects, define installed/portable data and log paths, and prove graceful/forced shutdown, no orphan, no console flash, repeated launch, startup failure cleanup, first run, reset, and state preservation semantics.
- **Why together:** these checks all observe one owned frontend/backend process and application-data lifecycle.
- **Expected evidence:** process trees, error/log readback, path inventory, repeat-launch results, and before/after state snapshots.
- **Dependencies:** G045 retention/recovery policy.
- **Desktop computer-use acceptance:** required for both installed and portable editions.
- **Release packaging/signing:** candidate-like unsigned or internal signed-preview artifacts may be required; public signing is not.
- **Validation scope:** targeted Rust/Python lifecycle tests plus the bounded computer-use matrix.

## G048 — Stable documentation, legal, privacy, and support readiness

- **Contract IDs:** `V1-SEC-006`, `V1-DOC-002`, `V1-DOC-003`, `V1-DOC-004`, `V1-DOC-005`, `V1-DOC-006`
- **Exact outcome:** publish stable user installation/portable/first-run/update/reset/uninstall/troubleshooting guidance; an evidence/review/remediation guide; supported Windows/runtime/display/upgrade matrix; third-party notice review; privacy/network disclosure; private security-reporting channel; and support/response policy.
- **Why together:** these are public promises and support boundaries that must use the same approved platform and state-lifecycle facts.
- **Expected evidence:** live-link readback, clean-reader walkthrough, support matrix, notices inventory/sign-off, and verified private-report workflow.
- **Dependencies:** G045 and G047 for accurate lifecycle/platform language.
- **Desktop computer-use acceptance:** only to verify documentation steps; no broad product retest.
- **Release packaging/signing:** not required.
- **Validation scope:** link/content checks and clean-reader execution of the documented flows.

## G049 — Whole-product accessibility and minimum-window baseline

- **Contract IDs:** `V1-DESKTOP-006`, `V1-UX-001`, `V1-UX-004`, `V1-UX-005`
- **Exact outcome:** define supported scaling; execute keyboard-only critical workflows; measure/review contrast and legibility; inspect all primary screens, long/error states, and modals at the minimum window; fix only confirmed v1 blockers.
- **Why together:** keyboard, focus, contrast, state meaning, and layout must be assessed as one pragmatic desktop baseline.
- **Expected evidence:** dated checklist, screenshots, contrast results, tab/focus observations, and targeted regression tests.
- **Dependencies:** G047 stable lifecycle/build and G048 declared support matrix.
- **Desktop computer-use acceptance:** required.
- **Release packaging/signing:** installed or portable candidate-like artifact required; public signing is not.
- **Validation scope:** focused frontend integration tests and bounded computer-use coverage.

## G050 — Release identity, dependency, format, and signer decisions

- **Contract IDs:** `V1-VER-004`, `V1-AGENT-003`, `V1-AGENT-006`, `V1-SEC-004`, `V1-REL-001`, `V1-REL-004`
- **Exact outcome:** expose honest runtime build/profile identity; record owner decisions for the 100-finding cap and remediation-format compatibility; replace loose npm production ranges with exact reviewed declarations without unrelated upgrades; close or time-bound-waive PostCSS alert #2; and obtain/configure an approved publicly trusted signing path without weakening the public-RC gate.
- **Why together:** these are explicit owner/release-authority decisions that must be settled before expensive public candidate construction.
- **Expected evidence:** runtime identity readback, committed decisions/expiry, GitHub alert/lockfile state, final artifact applicability plan, and successful disposable public-trust signer preflight.
- **Dependencies:** G048 owner/support process.
- **Desktop computer-use acceptance:** focused About/identity inspection only.
- **Release packaging/signing:** signer preflight required; no production artifact signing yet.
- **Validation scope:** targeted version, remediation boundary, dependency-resolution, and signing-preflight tests.

## G051 — v1 release-candidate construction and metadata

- **Contract IDs:** `V1-SEC-005`, `V1-REL-003`, `V1-REL-005`
- **Exact outcome:** construct the intended installer and portable candidate from one clean aligned commit, prove identical application payloads and exact inventories, and generate mutually consistent manifest, release metadata, and SHA-256 files without publishing a stable release.
- **Why together:** artifact bytes and their provenance/metadata must be created and frozen as one candidate transaction.
- **Expected evidence:** clean preflight, source commit, artifact inventory, identical-payload proof, portable re-extraction comparison, manifest, and independently recomputed hashes.
- **Dependencies:** G045–G050.
- **Desktop computer-use acceptance:** startup smoke only; full acceptance is G052.
- **Release packaging/signing:** release-candidate packaging required; use the approved signer path where the fail-closed pipeline requires it.
- **Validation scope:** release-script targeted tests plus candidate-only artifact verification.

## G052 — Clean-machine installed and portable acceptance

- **Contract IDs:** `V1-DESKTOP-002`, `V1-DESKTOP-003`, `V1-DESKTOP-004`, `V1-DESKTOP-005`, `V1-REL-006`
- **Exact outcome:** accept the frozen G051 candidate on every supported Windows environment for install, portable extraction/use, first run, repeat launch, backend shutdown, failure recovery, state location, upgrade, reset, uninstall, and documented troubleshooting.
- **Why together:** these are runtime properties of the exact candidate, not source-level promises.
- **Expected evidence:** dated clean-machine matrix, process observations, screenshots, state/path snapshots, signature checks, upgrade/uninstall results, and deviations.
- **Dependencies:** G051 frozen candidate and G048 support matrix/instructions.
- **Desktop computer-use acceptance:** required and central.
- **Release packaging/signing:** no rebuild; use only the frozen G051 artifacts.
- **Validation scope:** bounded acceptance checklist, not repository-wide tests.

## G053 — Final signing, artifact verification, and v1 authorization

- **Contract IDs:** `V1-SEC-005`, `V1-REL-004`, `V1-REL-005`, `V1-REL-006`
- **Exact outcome:** independently reverify every candidate PE signature and RFC 3161 timestamp, artifact hash/inventory/manifest/source alignment, release notes, GitHub Release contents plan, rollback/withdrawal procedure, and all contract closures; then request explicit owner authorization for v1.0.0.
- **Why together:** final authorization must operate on immutable accepted bytes and one complete evidence set.
- **Expected evidence:** independent verification report, signer/chain evidence, published hash/signing identity plan, rollback drill, final audit with no P0/P1, and explicit authorization.
- **Dependencies:** all previous handoffs, especially unchanged G051 bytes and passing G052 acceptance.
- **Desktop computer-use acceptance:** no new broad pass unless bytes or supported environment changed.
- **Release packaging/signing:** final verification required; no rebuild after acceptance. Git tag/GitHub Release creation occurs only in a separately authorized release action after this gate passes.
- **Validation scope:** artifact/evidence consistency and contract closure only.

## Recommended final order

1. **Gap remediation:** G045 → G046 → G047 → G048 → G049 → G050.
2. **Release-candidate construction:** G051 freezes traceable installer and portable bytes plus metadata.
3. **Installed and portable acceptance:** G052 exercises only those frozen bytes on the declared support matrix.
4. **Signing and artifact verification:** G053 independently verifies signatures, timestamps, hashes, inventory, manifest, source, and rollback readiness without rebuilding.
5. **Final v1.0 release authorization:** update the audit against the frozen candidate; proceed to tag and GitHub Release only if every release blocker passes and the project owner explicitly authorizes publication.
