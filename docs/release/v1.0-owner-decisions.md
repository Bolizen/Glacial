# Glacial v1.0 owner decisions

These decisions close the three explicitly waivable P2 items recorded by the
G044 v1.0 gap audit. Each decision becomes effective only after its G045
implementation and focused validation pass and the decision is committed.

## V1-DEC-001 — Retain the 100-finding remediation boundary

- **Date:** 2026-07-27
- **Status:** Accepted
- **Affected contract ID:** `V1-AGENT-003`
- **Decision:** Glacial v1.0 will retain the existing limit of at most 100
  unresolved findings in one Agent Remediation Brief or Agent Remediation
  Package.
- **Rationale:** A bounded handoff limits UI rendering, archive size, receiving
  agent context, resource use, and the scope of one remediation effort. Users
  can review or resolve findings iteratively and then produce a new
  snapshot-bound handoff.
- **Safety and compatibility constraints:**
  - The limit applies only to remediation preview and export scope. It does not
    limit scanning, storage, review, or display of the complete scan.
  - One canonical value controls the Brief and Package.
  - Included findings remain the first 100 findings in canonical
    severity-first, stable-identity order.
  - Exact unresolved, included, and omitted counts are always explicit. Glacial
    must never imply that a capped handoff contains every unresolved finding.
  - Exactly 100 unresolved findings has an omitted count of zero.
  - Review-state changes continue to invalidate stale exports.
  - Raising, removing, paginating, or batching the cap is post-v1 product work
    unless a confirmed defect requires earlier correction.
  - Future batching must preserve snapshot binding, deterministic ordering,
    omitted/range disclosure, and stale-state rejection.
- **Evidence required for closure:** Source inspection showing one canonical
  cap; focused 99, 100, 101, and mixed-severity over-limit tests; exact count
  agreement between Brief, `findings.json`, and `manifest.json`; deterministic
  ordering; and the existing stale-export regression.
- **Reconsider when:** A confirmed correctness or safety defect, unusable
  resource behavior, or an approved post-v1 pagination/batching design
  invalidates the bounded single-handoff model.
- **Duration:** Permanent for the Glacial v1.0 product boundary. A later product
  version may supersede it only through an explicit compatible design decision.

## V1-DEC-002 — Publish remediation format 1.x compatibility and retention

- **Date:** 2026-07-27
- **Status:** Accepted
- **Affected contract ID:** `V1-AGENT-006`
- **Decision:** The current Agent Remediation Package format remains `1.0.0`.
  Its semantic-version compatibility, reader, retention, deprecation, and
  generation-support rules are governed by
  `agent-remediation-format-policy.md`.
- **Rationale:** External consumers need a durable interpretation boundary that
  is independent of Glacial application versions, without inventing an archive
  importer or claiming unsupported cross-runtime reproducibility.
- **Safety and compatibility constraints:**
  - Published `1.x` meanings are not changed retroactively.
  - Patch updates correct output back to the existing contract without consumer
    adaptation; minor updates are safely ignorable additions; incompatible
    changes require a new major version.
  - Unsupported future major versions must be rejected clearly and safely by
    any future Glacial-owned reader or validator.
  - Project-derived content remains inert data, and rejection must not modify
    project files or existing Glacial state.
  - Format `1.x` generation remains supported throughout the Glacial v1
    application line unless a security issue requires an explicitly documented
    exception.
- **Evidence required for closure:** Published policy linked from existing
  remediation documentation; source-confirmed member inventory and format
  identifiers; existing package determinism, checksum, data-only, path-safety,
  and stale-state tests; and an explicit statement that Glacial has no current
  remediation-archive importer.
- **Reconsider when:** A successor major format is designed, a security issue
  makes continued generation unsafe, or Glacial introduces an owned reader or
  validator that requires executable compatibility tests.
- **Duration:** Permanent for already published format semantics and archive
  interpretation. The documented generation-support duration applies to the
  Glacial v1 application line.

## V1-DEC-003 — Remediate PostCSS rather than waive the advisory

- **Date:** 2026-07-27
- **Status:** Accepted
- **Affected contract ID:** `V1-SEC-004`
- **Decision:** Resolve Vite's transitive PostCSS path to exact version
  `8.5.18`, the first version fixed for `GHSA-r28c-9q8g-f849`, using a narrow
  npm override. No waiver is authorized.
- **Rationale:** Vite 7.3.6 accepts PostCSS `^8.5.6`; PostCSS 8.5.18 preserves
  the dependency and Node-engine contract of 8.5.16 while removing the
  advisory-affected resolution. An exact override is smaller than a Vite
  upgrade and does not convert PostCSS into a shipped application dependency.
- **Safety and compatibility constraints:**
  - The override is exact and must not change unrelated package resolutions.
  - Vite and the existing loose production declarations remain otherwise
    unchanged; exact production declarations are still tracked by
    `V1-REL-001`.
  - `package-lock.json` integrity remains authoritative.
  - PostCSS remains build tooling. Tauri consumes `frontend/dist`, and release
    inventory rules exclude `node_modules`.
  - A production frontend build and dependency-tree readback must pass.
- **Evidence required for closure:** Authoritative alert readback, reviewed
  package and lockfile diff, `npm ls`/`npm explain` showing only PostCSS 8.5.18,
  absence of any vulnerable PostCSS resolution, and a successful production
  frontend build.
- **Reconsider when:** A newer advisory affects the selected version, Vite's
  supported PostCSS range changes, the build path begins processing untrusted
  project CSS, or final artifact inventory unexpectedly includes build
  dependencies.
- **Duration:** Permanent remediation for this advisory. The selected version
  may be superseded only by a separately reviewed non-vulnerable resolution.
